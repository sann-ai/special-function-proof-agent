# Special Function Proof Agent: Codex instructions

These rules apply throughout this project.

- Codex is the user's conversation interface; this repository is the local verification engine. For a proof request, follow [the Codex workflow](docs/codex-workflow.md). Accept natural language or TeX, create the supported structured input yourself, run the tools, and return the result in the user's language. Do not require the user to write JSON or execute routine commands.
- Check setup with `python3 scripts/doctor.py` when needed. Use the fixed setup instructions; do not change global Codex settings, install skills, add dependencies, or edit this project's implementation for an ordinary proof request.
- State the interpreted formula, variable types, conventions and all supplied assumptions concisely, then proceed when clear. Ask only about mathematical ambiguity or a condition needed to change the requested scope. Keep an unconditional request unchanged when reporting missing conditions or unsupported input.
- The current Codex conversation prepares and verifies plans directly. Default to `verify --route steps` when the user asks for an explanation, otherwise use the requested route. Use the separate `generate` command only when the user explicitly asks for that standalone generator; do not recursively launch Codex for an ordinary conversation.
- Write work files into a fresh ignored `runs/` directory, preserve the original user text beside the fixed target, and keep artifacts out of Git. Save to the external archive within the user's authorized scope. If saving/reuse and its location were already established in the conversation or research settings, continue without asking again. For a new user whose archive location is unspecified, ask only about that location and suggest `~/SpecialFunctionProofAgentData/archive`. For authorized history reuse, call `archive lookup TARGET --route steps|direct`; reuse only a `proved` result with `replayed: true`. A miss or rejected record is a search result, not a verdict on the formula.
- Read the resulting `result.json`, `report.md`, and successful `certificate.lean` before reporting. Give the exact formula/conditions, proof scope, concise Japanese equality steps when requested, and links to the report and formal certificate. Report numerical diagnostics separately; for unresolved input give the specific missing condition, unsupported form, or failed verification. Mention archive ID/replayed status only when actually returned.
- Preserve the exact input target: variable names and types, bindings, all assumptions, function definitions and conventions. Ask for a missing mathematical condition before adopting it.
- Parse text with `python3 -m special_function_agent parse`; inspect the saved target before proposing a proof plan.
- Use `verify --route direct` or `verify --route steps` for the local registered Gamma/Beta/Hermite/erf, Legendre/Laguerre/Jacobi, half-integer YNoninteger, integer-Y recurrence/argument derivative/Wronskian and cross-root recipes. For a composed plan, use only the existing allowlisted structured proof schema and verify its fixed target.
- Hermite H uses the physicists convention; He uses the probabilists convention. Hermite/Legendre/Laguerre/Jacobi require natural degree and the stated lower bound for a predecessor degree. Polynomial degrees m and n are natural; preserve each type and comparisons such as m!=n. Bessel degree variable n remains integer. Preserve all real polynomial parameters and the alpha=0 ordinary Laguerre convention; see [orthogonal polynomial definitions](docs/orthogonal-polynomials.md) and [recurrences, orthogonality and normalization](docs/polynomial-calculus.md). Erf and its Gaussian finite-interval formulas use all real arguments/endpoints.
- A derivative fixes every other free real variable. Preserve parameter dependence and use distinct generated binders for nested derivatives and integrals.
- The verifier owns the theorem and the Lean translation. A proof candidate contains only the closed recipe/step schema; it cannot replace a target, add assumptions, or submit arbitrary Lean code.
- Keep the original theorem, explicitly conditional analytic/algebraic certificates, and numerical diagnostics separate. Report `proved` only after the fixed full target passes Lean and the standard-axiom audit.
- The explicit `YNoninteger` AST supports orders -1/2, 1/2, 3/2 and x>0 for its recurrence and derivative. Legacy `Y_n` supports the exact integer recurrence and adjacent-order Wronskian for n: int, x>0, and Y0/Y1 argument derivatives for x>0. Order differentiability, mixed differentiation, the standard integer limit, and the Wronskian normalization are proved. Preserve the signs: J1*Y0-J0*Y1=2/(pi*x), while X01(x,x)=-2/(pi*x). Full Lean acceptance sets `full_bessel_proof: true`. Unsupported two-point cross-products and Y inputs retain their explicit obligations. Saved diagnostic certificates retain their original premises; explicitly verify the target with direct/steps to create a new complete proof. See [Bessel Y scope](docs/bessel-y-formalization.md).
- The exact cross-root fraction uses z>0, 0<lambda<1, X01(z,lambda*z)=0. Preserve X02 at the end of its left denominator and X00 without a derivative in its right numerator. The registered Lean proof derives positive energy and both denominators nonzero from those original conditions. Missing root or interval conditions must not be supplied by a candidate. Explicit diagnostic records retain their historical conditional scope.
- Use only `propext`, `Classical.choice`, and `Quot.sound`. Preserve the `sorry` and dependency audit.
- Archive data belongs outside this repository, by default in `~/SpecialFunctionProofAgentData/archive`. Recheck saved certificates against the current mathematical environment before reuse.
- Research lemmas belong outside this repository in `~/SpecialFunctionProofAgentData/research`. Use `research add` and `research verify|generate --using ID` to apply fully proved real lemmas to a different fixed target; discharge every source assumption from that target's original conditions. Regenerate certificates from closed plans, preserve dependency IDs and bindings, and reverify after environment changes. Export only the package selected by the user, including its disclosed dependency evidence. See [research lemmas](docs/research-lemmas.md).
- Finite research functions use `research function add` and typed JSON calls by semantic definition ID. Keep original calls, definitions, parameters and conditions in the target; Lean must connect them to the expanded theorem. Definitions have status `defined`; each claimed identity needs its own proof. Preserve dependency snapshots and old records; use explicit reverify after environment changes. See [research functions](docs/research-functions.md).
- Analytic research definitions currently use three closed forms: `exp_series` for sum x^n/n!, `gaussian_primitive` for the oriented integral of exp(-t^2) from 0 to x, and `linear_ivp` for the unique global real solution of y'=rate*y, y(0)=initial. Registration must certify convergence, integrability, or existence and uniqueness as applicable. Preserve these contracts and the scoped analytic-module hash; see [analytic research definitions](docs/research-analytic-definitions.md). Build `lake build SpecialFunctionProofAgent.AnalyticDefinitions` alongside the base project.
- User analytic expressions use `series_definition` (finite linear combinations of q^n/n!), `integral_definition` (polynomial integrand, arbitrary real endpoints), and `ode_definition` (polynomial p(t)*y, arbitrary real initial time/value). Prove the original term/integrand/RHS equals its normalized form, retain scalar domain obligations through cancellations, and certify HasSum, integrability, or global existence/uniqueness before registration. Keep internal natural/time/state binders separate from parameters. Build `lake build SpecialFunctionProofAgent.UserAnalyticDefinitions`; preserve its scoped hash and old evidence. See [user analytic definitions](docs/research-user-analytic-definitions.md).
- Advanced user definitions use `geometric_series_definition`, `elementary_integral_definition`, `nonlinear_ode_definition`, and `second_order_ode_definition`. Preserve their bounded input classes: certified geometric bases, fixed rational affine slopes, polynomial-times-sqrt nonlinear state kernel, and polynomial second-order forcing with independent position/velocity initial values. Certify convergence/integrability/global existence and uniqueness, connect every original expression to its normal form, and keep `AdvancedAnalyticDefinitions.lean` fingerprinted only for consumers. See [advanced analytic definitions](docs/research-advanced-analytic-definitions.md).
- Import Bessel evidence only through explicit `archive import-bessel`; preserve source environment and provenance and reverify in this project.
- The numerical backend is optional. When existing mpmath is unavailable, save `backend_unavailable` and continue supported symbolic/formal checks. Do not install dependencies without authorization.
- Keep changes small. Run focused tests, then `SF_RUN_LEAN_TESTS=1 BESSEL_RUN_LEAN_TESTS=1 python3 -m unittest discover -s tests -v`, `lake build`, `python3 scripts/audit_special_functions.py`, and `python3 scripts/replay_examples.py` for release validation.
- Keep user inputs, private archives, credentials, generated local runs and account metadata out of Git.
